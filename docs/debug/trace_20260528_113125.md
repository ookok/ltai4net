## Response

一个查询如果不使用索引而直接进行全表扫描，性能的变化是双面的：它可能让某些查询**快如闪电**，也可能让另一个查询**慢到崩溃**。要透彻理解这个变化，需要从数据库内核的 I/O、CPU、内存与并发四个层面，并对比两种数据访问路径的本质差异。

### 1. 本质差异：顺序读 vs 随机读 + 回表
- **全表扫描 (Full Table Scan)**  
  数据库按照物理存储顺序，将整个表的 **所有数据页** 一次性读入内存。通常使用**多块读**（如 MySQL 中一次读 1MB 的 extent），是 **顺序 I/O**，吞吐量极大。处理时逐行检查是否符合过滤条件。

- **索引扫描 (Index Scan/Seek)**  
  先遍历 B+Tree 的树结构定位叶节点（几次随机读），获取符合条件行的物理地址（或主键），再**回表**去聚簇索引/堆表中取完整行数据，每次回表都是一次 **随机 I/O**。如果最终返回的行数较多，随机读的成本会指数级上升。

### 2. 性能变化的多维度剖析
假设一张 `orders` 表，1000 万行，每行约 200 字节，存储在 20 万个 16KB 的数据页中（MySQL InnoDB 为例）。

#### 2.1 磁盘 I/O：从随机到顺序的剧烈转变
| 场景 | 索引访问（随机读） | 全表扫描（顺序读） | 性能变化 |
|------|-------------------|-------------------|----------|
| 返回 1 行（选择性极高） | 3~4 次树搜索 + 1 次回表，共 **<10 次随机读**，可能全在缓存 | 需要依次读 **20 万个数据页**，物理 I/O 极大 | **全表扫描性能崩溃**，从毫秒级变为分钟级 |
| 返回 50% 的数据（500万行） | 需要几十万次回表随机读，磁头疯狂寻道 | 仍然是 20 万页的顺序读，且多块读可预读 | **全表扫描可能快数倍至数十倍**，因为避开了随机 I/O 的代价 |

**关键原因**：机械硬盘随机 I/O 的 IOPS 仅 100~200，而顺序带宽可达 200MB/s。即使 SSD 大幅降低了随机延迟，顺序读仍然在吞吐量和高队列深度下碾压大量随机单块读。

#### 2.2 CPU 与过滤成本
- **全表扫描**：CPU 需要遍历 **所有行** 评估 `WHERE` 条件，消耗大量 CPU 周期。若条件复杂（如正则、函数），更会加剧 CPU 瓶颈。
- **索引扫描**：利用 B+Tree 有序性，可直接定位子树或执行 Index Condition Pushdown（ICP），**大幅度减少需要评估的行数**，CPU 开销通常更低（除非返回比例极高）。

#### 2.3 内存与缓冲池污染
全表扫描会触发 **缓冲池污染**：数据库会将庞大表的所有页面载入 Buffer Pool，并因扫描算法（如 MySQL 的 `innodb_old_blocks_time`）很可能将原本缓存的热点数据挤出内存，导致**整个应用性能出现瞬时下降**。索引扫描只加载少数所需页，对其他查询几乎无影响。

#### 2.4 并发与锁的恶化
- 全表扫描在多数引擎中会获取表级意向锁或逐行加锁，如果一个长扫描在 `REPEATABLE READ` 下长时间未提交，会阻塞对该表的更新操作，甚至导致死锁。
- 索引扫描细粒度更小，只触及需要的行。

### 3. 何时“不使用索引”反而是正确的选择
不是不用索引就糟糕！优化器有时会故意忽略索引去全表扫描，常见场景包括：
- **返回数据占比高**（通常超过 15%~30%，由优化器根据统计信息计算成本）。
- **表极小**（例如只有几个页面，扫描全表成本低于两次索引搜索）。
- **索引不是覆盖索引，需要回表成本太高**：如果查询需要索引不包含的列，回表随机读的累计代价会迫使优化器转全表扫描。
- **索引键分布极不均匀**（如仅几个值），优化器认为索引定位后仍需扫描大量行。
- **查询中包含对索引列使用了函数或隐式转换**，导致索引失效，只能被迫全表扫描。此时性能会从预期极速骤降为慢查询。

### 4. 当强制全表扫描时，性能会经历什么？
若你通过 `IGNORE INDEX` 或当索引失踪时，一个典型的大表点查性能变化如下：
- **响应时间**：从 0.01 秒 → 30 秒甚至超时。
- **IO 等待**：`iostat` 看到磁盘读带宽暴涨、队列深度满。
- **CPU**：%user 升高，因为大量无谓的行解析。
- **应用表现**：连接池被占用时间变长，爆发雪崩。数据库 `Threads_running` 飙升。

### 5. 如何预判并决策
使用 `EXPLAIN` 查看执行计划，关注：
- **rows**：预估扫描行数。如果与表总行数接近，是全表扫描。
- **Extra**: `Using where` 说明在存储引擎层逐行过滤，无索引加速；`Using index` 是覆盖索引，应优先使用。
- 计算选择性：`区分度 = 过滤后行数 / 表总行数`。<10% 时通常索引更优；>30% 时全表扫描更优；中间地带依赖硬件和缓存状态。

**最佳实践**：
- 为大表上的高频点查/范围查建立合适索引，尽量让查询成为**覆盖索引扫描**，避免回表。
- 定期更新统计信息（`ANALYZE TABLE`），让优化器能准确估算成本，避免“该全扫时错用索引”或“该索引时误走全扫”。
- 对于必须全表扫描的大结果集，考虑并行查询（如 PostgreSQL 的 `parallel seq scan`）或把负载转移到读副本，以物理顺序读充分发挥 I/O 潜力。

**总结**：直接全表扫描的本质是在**用高吞吐的顺序 I/O 换取对行过滤的代价**。在返回大量行时，这可能是最优解，性能会比强行索引+回表提升数倍；但在高选择性、毫秒级响应要求下，它会让数据库资源耗尽、性能崩塌。因此，没有绝对的好与坏，一切都取决于数据规模、过滤比例和物理设计。
