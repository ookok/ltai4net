### 1. 提示词工程优化（Prompt Engineering）

**1.1 结构化任务描述**  
使用精确、约束清晰的提示模板，避免模糊表达，强制模型输出符合预期的格式。
- 明确指定语言、库版本、函数签名、输入输出类型。
- 给出具体的成功标准，例如“必须通过所有测试用例”。

**1.2 思维链与分步规划（Chain-of-Thought & Plan-and-Solve）**  
要求模型先输出解决思路、伪代码或步骤，再生成最终代码。这能显著减少逻辑跳跃导致的错误。
```
你是一位严谨的程序员。请按以下步骤回答：
1. 分析问题，总结需求。
2. 描述算法思路与关键数据结构。
3. 写出伪代码。
4. 将伪代码翻译为最终的 Python 代码。
问题：…
```

**1.3 最少示例与约束示例（Few-shot & Constrained Examples）**  
提供 2-3 个同类的“需求-计划-代码”高质量示例，并刻意在示例中包含常见陷阱的正确处理方式（如边界检查、异常处理），引导模型学习鲁棒模式。

**1.4 角色设定与防御性编程提示**  
增加角色指令，强制模型考虑边界条件、错误输入，并添加必要的断言与日志。  
例如：“你写的代码必须处理空列表、负数等异常情况。在关键位置添加注释和断言。”

### 2. 知识增强与检索（RAG & Context Enrichment）

**2.1 库文档实时检索**  
对于涉及特定框架或库的任务，通过检索增强生成（RAG）将官方文档片段作为上下文注入。这能防止模型幻觉出不存在的 API，并准确掌握参数用法。

**2.2 代码库示例检索**  
从企业内部库或开源仓库中检索相似功能的实现，作为参考嵌入提示。使用向量数据库（如 Chroma、Pinecone）索引代码片段，依据需求相似度动态召回。这帮助模型输出风格一致、依赖于内部实用函数的正确代码。

**2.3 依赖与类型定义注入**  
将与任务相关的类型定义、接口声明、常量列表提前放入提示，确保生成代码能真正编译或通过静态检查。

### 3. 推理与分解强化

**3.1 复杂问题分解（Decomposition）**  
面对长需求，先用一个“分解模型”或提示模板将大问题拆解成多个独立函数/步骤，再分别生成各部分的代码。最后生成整合代码。这能够降低单次生成的认知负载，提高每个子模块的正确率。

**3.2 算法自我验证**  
在生成代码后，让模型自己模拟执行几个简单的测试用例，以自然语言逐步推导变量状态，并与期望结果比较。这种“心智执行”能提前过滤掉简单逻辑错误。

### 4. 测试驱动的反馈闭环（Execution Feedback Loop）

这是提升代码实际可运行性与正确率最有效的手段之一。

**4.1 测试先行生成（Test-Code Generation）**  
- 先根据需求生成一套全面的测试用例（包含常规输入、边界值、异常输入）。
- 将这些测试用例连同需求一起交给代码生成模型，要求生成的代码必须通过提供的测试。
- 相当于用“可执行规范”替代模糊的自然语言需求。

**4.2 自我调试（Self-Debugging / Self-Reflection）**  
将生成代码在实际解释器/编译器中执行，获取报错信息或失败的测试结果，然后将错误信息反馈给模型，让其修复。循环进行直到通过全部测试或达到最大迭代次数。
```
[系统] 你的代码运行后报错：
TypeError: unsupported operand type(s) for +: 'int' and 'str'
请分析原因并给出修正后的完整代码。
```

**4.3 执行轨迹反馈**  
对于使用外部 API 或复杂计算的任务，可以收集真实的返回值或中间状态，与预期轨迹对比，将差异作为提示反馈，引导模型精准修正逻辑。

**4.4 AlphaCodium 式流程**  
Meta 提出的 AlphaCodium 是一种多阶段代码生成流程，核心在于：  
1. 对问题深度解析（自问自答，揭示约束）。  
2. 生成初步解决方案与多种可能的算法思路。  
3. 生成大量测试用例并进行排序。  
4. 迭代地在公共测试和生成测试上运行代码，收集输出与错误，不断改进代码。  
这种方法将正确率提升到了新高度，值得工程化借鉴。

### 5. 采样与一致性选择（Sampling & Reranking）

**5.1 多次采样 + 测试过滤**  
对同一需求生成多个候选解（如温度设为 0.6~0.8，生成 10~20 个），在隔离沙箱中运行所有的测试用例，筛选出完全通过测试的解。如无完美解，可选择通过用例最多的版本作为基础，继续修复。

**5.2 投票一致性（Majority Voting on Execution Results）**  
针对每个测试输入，运行所有候选解，取输出结果出现频率最高的作为最终答案。这种方法对易于出现非确定性错误的模型尤其有效。

**5.3 基于正确性模型的排序**  
训练一个轻量的打分模型（或使用代码大模型评估），专门评估“代码能否正确解决问题”，对候选列表进行排序，再提交测试。这比随机选择或单纯基于困惑度排序更准确。

### 6. 模型与微调策略

**6.1 选择强代码基模型**  
基础模型的能力天花板至关重要，选用在代码理解/生成上优化的模型（如 DeepSeek-Coder、Code Llama、StarCoder、GPT-4 等）。模型对主流库和语法的掌握程度直接决定初始正确率。

**6.2 领域微调（Fine-tuning on Execution Feedback）**  
如果允许微调，可构建“指令-代码-测试结果”三元组数据集，训练模型从错误反馈中自我修复。更进一步的 STaR（Self-Taught Reasoner）方法：用执行反馈筛选出正确的“推理+代码”对，再迭代微调，使模型学会“先推理再编码”的正确模式。

**6.3 强化学习对齐（RLHF/GRPO）**  
通过编译/测试正确性作为奖励信号，使用 PPO 或 GRPO 等方式优化模型，将正确率直接纳入训练目标。这是 DeepSeek-R1 等模型中数学/代码能力突破的关键技术之一。

### 7. 工具集成与智能代理架构

**7.1 编译器/Linter 即时反馈**  
将生成代码送入语法检查工具（如 Pylint, ESLint, ShellCheck），把警告和错误作为环境观测输入，让模型修正。这能消除低级拼写和语法错误。

**7.2 沙箱执行环境**  
构建安全的 Docker 或 WebAssembly 沙箱，提供文件系统和网络限制，用于真实运行代码、捕获异常并计时。这是实现自我调试闭环的基础设施。

**7.3 代理型工具调用（Function Calling）**  
允许模型在生成过程中主动调用“搜索库文档”、“运行测试”、“查看执行输出”等工具，形成 ReAct 或 Tool-augmented 代理循环。通过让模型自主探索所需信息，减少上下文盲猜，可显著提升复杂 API 调用的正确率。

### 综合优化流水线建议

**最优实践往往是多策略融合**，推荐如下流水线：

1. **需求提炼**：模型分析需求，产出结构化约束和明确的接口签名。  
2. **测试生成**：生成全面的测试用例（常规+边界+异常）。  
3. **多路代码生成**：使用带 RAG 知识的 Plan-and-Code 提示，以中高温度并行生成 N 个候选。  
4. **编译/静态检查过滤**：剔除所有存在语法错误或类型不匹配的候选。  
5. **沙箱执行与排名**：对剩余候选执行测试用例，按通过数量排序。  
6. **迭代修复**：若最佳候选未全通过，进入 Self-Debugging 循环（结合错误信息和测试失败详情），直至通过或达到上限。  
7. **输出最优解**，并附带通过的测试报告。

这种流水线将“生成”转变为“生成+验证+修复”，使正确率获得量级提升，尤其适合对正确性有严格要求的自动化代码生成场景。
