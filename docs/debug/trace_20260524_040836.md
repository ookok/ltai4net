## 1. 总体设计思路
分布式环境下，多个服务实例共享限流状态，需要一个集中式存储。这里选用 Redis，因为它高性能、原子操作支持好。通过 Lua 脚本保证操作的原子性，避免并发竞态。

## 2. 滑动窗口限流
### 2.1 算法原理
使用 Redis 的有序集合（Sorted Set），以用户/接口标识作为 key，member 为请求的唯一 ID 或时间戳，score 为请求的毫秒时间戳。
每次请求时：
1. 移除窗口外（当前时间 - 窗口长度）的旧记录。
2. 统计集合中剩余的元素个数。
3. 若个数未达上限，将当前请求的时间戳加入集合并设置过期时间，允许通过；否则拒绝。

### 2.2 Lua 脚本
```lua
-- 滑动窗口限流脚本
-- KEYS[1]: 限流 key
-- ARGV[1]: 窗口大小（毫秒）
-- ARGV[2]: 当前时间戳（毫秒）
-- ARGV[3]: 请求上限
-- ARGV[4]: 请求唯一标识（如 GUID）
-- 返回: 1表示允许，0表示拒绝

local key = KEYS[1]
local window = tonumber(ARGV[1])
local now = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])
local request_id = ARGV[4]

-- 移除过期的请求
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)

-- 获取当前窗口内的请求数
local count = redis.call('ZCARD', key)

if count < limit then
    redis.call('ZADD', key, now, request_id)
    -- 设置过期时间，避免 key 永不删除
    redis.call('PEXPIRE', key, window)
    return 1
else
    return 0
end
```

## 3. 令牌桶限流
### 3.1 算法原理
以固定速率向桶中添加令牌，桶有最大容量。请求到达时，若桶中有足够令牌则取走并放行，否则拒绝。
在 Redis 中存储：
- `tokens`：当前可用令牌数（初始为 0 或容量）
- `last_refill`：上次填充时间戳
每次请求时，先根据速率计算从上次填充到现在应生成的令牌数，更新令牌数（不超过容量），然后判断是否足够。

### 3.2 Lua 脚本
```lua
-- 令牌桶限流脚本
-- KEYS[1]: 桶 key
-- ARGV[1]: 容量（最大令牌数）
-- ARGV[2]: 速率（令牌/秒）
-- ARGV[3]: 当前时间戳（毫秒）
-- ARGV[4]: 请求消耗的令牌数
-- 返回: 1允许，0拒绝

local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local requested = tonumber(ARGV[4])

-- 获取当前状态
local bucket = redis.call('HMGET', key, 'tokens', 'last_refill')
local tokens = tonumber(bucket[1]) or capacity
local last_refill = tonumber(bucket[2]) or now

-- 计算应补充的令牌
local elapsed = now - last_refill
local refill = math.floor(elapsed * rate / 1000.0)  -- 速率是每秒，elapsed是毫秒

if refill > 0 then
    tokens = math.min(capacity, tokens + refill)
    last_refill = now
end

-- 判断令牌是否足够
if tokens >= requested then
    tokens = tokens - requested
    redis.call('HMSET', key, 'tokens', tokens, 'last_refill', last_refill)
    -- 设置过期时间，避免长期空闲的 key
    redis.call('PEXPIRE', key, 10000)  -- 10秒，视情况调整
    return 1
else
    redis.call('HMSET', key, 'tokens', tokens, 'last_refill', last_refill)
    redis.call('PEXPIRE', key, 10000)
    return 0
end
```

## 4. 对比分析
| 维度 | 滑动窗口 | 令牌桶 |
|------|----------|--------|
| **精准度** | 统计窗口内请求数，边界清晰，严格限制突发 | 允许一定程度的突发（桶容量），但突发后会被平滑限流 |
| **实现复杂度** | 稍高，需维护有序集合，移除过期数据 | 中等，只需维护两个字段，计算补充令牌 |
| **内存占用** | 较高，每个请求在 Redis 中至少存储一个 member，高流量时可能引起大 key 问题 | 极低，每个限流 key 仅存储两个数字 |
| **性能** | ZCARD、ZADD 等操作在集合较大时性能略有下降 | 仅 HMGET/HMSET，性能稳定 |
| **突发处理** | 不允许突发，严格按窗口限制，瞬时流量不能超过阈值 | 支持短时突发，最大突发量由桶容量决定，适合需要吸收峰值的场景 |
| **适用场景** | 严格 API 调用频率控制（如用户每分钟最多 100 次），对公平性要求高的场景 | 网络流量整形、允许弹性突发但总体速率受控的场景（如短信发送、下载限速） |
| **分布式注意事项** | 依赖时间戳，要求各节点时钟大致同步（偏差应远小于窗口），否则可能出现不公平 | 同样依赖时间戳补充令牌，但对时钟偏差的容忍度稍高（误差只会影响一次补充量） |

## 5. 优缺点总结
**滑动窗口**
- 优点：准确直观，能够精确反映最近一段时间内的负载，适合严格的配额控制。
- 缺点：内存消耗大，高 QPS 场景下 Redis 有序集合可能膨胀；清理旧数据有额外开销；窗口边界可能存在“双倍请求”现象（可通过平滑处理缓解，但本文的实现是窗口内严格计数）。

**令牌桶**
- 优点：内存占用小，支持弹性突发，算法执行效率高，非常适合平滑流量和允许峰值的场景。
- 缺点：不能精确限制短时间内请求的严格数量，突发量受桶容量限制；长期速率稳定，但瞬时可能冲破期望的均匀分布。

## 6. 适用场景建议
- **滑动窗口**：API 频率限制、账户操作次数限制（如登录尝试）、需要明确告知用户“你在最近 N 秒内还能请求 X 次”的场景。
- **令牌桶**：网关流量整形、消息队列消费控制、防止下游服务过载的同时允许适当突发，或者需要提供“积攒”配额功能的场景（如用户可积累一定请求额度）。

以上实现均已封装为 C# 类，可直接在依赖 Redis 的分布式系统中使用。实际部署时需注意 Redis 的高可用和时钟同步。
