## 什么是 SOLID 原则？

SOLID 是面向对象编程中五个非常重要的设计原则，它们的目的是让软件更容易维护、扩展和理解。

| 缩写 | 原则                      | 核心思想                                                     |
|------|---------------------------|--------------------------------------------------------------|
| S    | 单一职责原则 (SRP)        | 一个类应当只有一个引起它变化的原因。                             |
| O    | 开闭原则 (OCP)            | 软件实体（类、模块、函数等）应该对扩展开放，对修改关闭。           |
| L    | 里氏替换原则 (LSP)        | 子类必须能够替换它们的基类，且不会引起程序异常。                   |
| I    | 接口隔离原则 (ISP)        | 客户端不应该被迫依赖它们不使用的方法，接口应当小而专一。           |
| D    | 依赖倒置原则 (DIP)        | 高层模块不应该依赖低层模块，两者都应该依赖抽象；抽象不应该依赖细节，细节应该依赖抽象。 |

## 重构示例：从一个违反所有 SOLID 原则的类开始

假设我们有这样一个处理订单的类（用类似 Java 的伪代码），它几乎违反了所有 SOLID 原则：

```java
// 一个超级大的类，什么都做
public class OrderProcessor {
    // 直接访问数据库
    private DatabaseConnection db = new DatabaseConnection();
    
    // 处理订单，同时包含：验证、计算折扣、支付、记录日志、发送邮件
    public void process(Order order) {
        // 1. 验证订单
        if (order.getItems().isEmpty()) {
            throw new RuntimeException("Order has no items");
        }
        if (order.getCustomer() == null) {
            throw new RuntimeException("Customer is missing");
        }
        
        // 2. 计算总价和折扣
        double total = 0;
        for (Item item : order.getItems()) {
            total += item.getPrice() * item.getQuantity();
        }
        double discount = 0;
        if (order.getCustomer().isVip()) {
            discount = total * 0.1;
        }
        double finalAmount = total - discount;
        
        // 3. 处理支付（根据支付类型判断）
        if (order.getPaymentMethod().equals("CreditCard")) {
            CreditCardPayment ccPayment = new CreditCardPayment();
            ccPayment.pay(order.getCreditCardInfo(), finalAmount);
        } else if (order.getPaymentMethod().equals("PayPal")) {
            PayPalPayment ppPayment = new PayPalPayment();
            ppPayment.pay(order.getPayPalAccount(), finalAmount);
        } else {
            throw new RuntimeException("Unsupported payment method");
        }
        
        // 4. 保存订单到数据库
        db.save(order, finalAmount);
        
        // 5. 记录日志
        Logger logger = new FileLogger();
        logger.log("Order processed: " + order.getId() + " amount: " + finalAmount);
        
        // 6. 发送邮件通知
        EmailService email = new EmailService();
        email.send(order.getCustomer().getEmail(), "Your order has been processed", "Details...");
    }
}
```

**这段代码存在哪些问题？**

- **单一职责 (SRP)** 严重违反：一个类同时负责订单验证、价格计算、支付、持久化、日志、邮件通知。
- **开闭原则 (OCP)** 违反：当需要新增一种支付方式（比如加一个 ApplePay）时，必须修改 `process` 方法内的 if-else 块。
- **里氏替换 (LSP)** 暂无明显继承关系，但如有子类可能出问题。
- **接口隔离 (ISP)** 未体现，但如果我们抽象出接口，可能会定义得过于臃肿。
- **依赖倒置 (DIP)** 严重违反：`OrderProcessor` 直接依赖于具体的低级模块：`DatabaseConnection`、`CreditCardPayment`、`FileLogger`、`EmailService`，而不是依赖抽象。

## 重构过程（逐步引入 SOLID 原则）

### 第一步：应用单一职责原则 (SRP) —— 拆分类职责

我们将 `OrderProcessor` 的大管家职责拆分成多个更小、更专注的类或服务。

- **OrderValidator**：只负责订单验证
- **PriceCalculator**：负责价格计算和折扣逻辑
- **PaymentProcessor**：负责发起支付（但之后会用策略模式处理 OCP）
- **OrderRepository**：负责订单持久化
- **NotificationService**：负责发送通知（日志和邮件可以再分开，但先合并）

重构后的“指挥者”类会叫 `OrderService` 或 `OrderFacade`，它只负责协调这些服务。

### 第二步：应用依赖倒置原则 (DIP) 和接口隔离原则 (ISP)

为每个功能定义接口，让高层模块依赖这些接口，而不是具体实现。

```java
// 定义各种接口（小而专一）
public interface OrderValidator {
    void validate(Order order);
}

public interface PriceCalculator {
    double calculate(Order order);
}

public interface PaymentService {
    void pay(Order order, double amount); // 付款
}

public interface OrderRepository {
    void save(Order order, double finalAmount);
}

public interface NotificationService {
    void notify(Order order, double finalAmount);
}

// 然后提供各自的实现类，实现这些接口
```

### 第三步：应用开闭原则 (OCP) —— 让扩展支付方式变得容易

原来的 if-else 害我们必须修改代码。我们可以引入策略模式，并让 `PaymentService` 的实现根据订单的支付方式动态选择。

一种做法是让 `PaymentService` 的实现内部使用一个 `PaymentMethod` 接口和多个实现类：

```java
public interface PaymentMethod {
    void pay(PaymentDetails details, double amount);
}

public class CreditCardPayment implements PaymentMethod { ... }
public class PayPalPayment implements PaymentMethod { ... }

// PaymentProcessorImpl 可以持有一个 Map<String, PaymentMethod> 或使用工厂，但更好的方式是使用依赖注入。
```

更进一步，我们可以为每种支付方式创建一个实现了 `PaymentService` 的类，然后在运行时通过策略选择。不管怎样，新增支付方式时，我们只需新加一个类，而无需修改已有的代码。

### 第四步：应用里氏替换原则 (LSP) —— 确保子类可以安全替换

当我们有继承关系时，必须保证子类遵守父类的约定。例如，如果我们有一个 `VipPriceCalculator` 继承 `BasePriceCalculator`，它不应该改变父类 `calculate` 方法的预期行为（比如不应该抛出新的异常或改变返回值的意义）。

在我们的重构中，一般会使用接口+组合，减少继承的使用，从而减少违反 LSP 的风险。如果必须使用继承，要确保子类的行为完全符合基类契约。

### 第五步：接口隔离原则 (ISP) 的再次检查

注意我们定义的接口 `NotificationService` 只有一个 `notify` 方法，它负责日志和邮件。但如果我们有不同客户端，有的只需要日志通知，有的只需要邮件，就不希望被迫依赖不需要的方法。这时可以进一步拆分为：

```java
public interface Logger {
    void log(String message);
}
public interface EmailNotifier {
    void sendEmail(String to, String subject, String body);
}
```

然后 `NotificationService` 可以由组合这两个接口来实现。这样客户端可以只依赖他们所需要的接口。

## 最终重构后的代码（骨架）

```java
// 协调者，依赖于抽象接口
public class OrderService {
    private final OrderValidator validator;
    private final PriceCalculator calculator;
    private final PaymentService paymentService;
    private final OrderRepository repository;
    private final NotificationService notification;
    
    // 构造函数注入（依赖倒置）
    public OrderService(OrderValidator validator, 
                         PriceCalculator calculator, 
                         PaymentService paymentService,
                         OrderRepository repository,
                         NotificationService notification) {
        this.validator = validator;
        this.calculator = calculator;
        this.paymentService = paymentService;
        this.repository = repository;
        this.notification = notification;
    }
    
    public void process(Order order) {
        validator.validate(order);                 // 单一职责：验证
        double finalAmount = calculator.calculate(order); // 单一职责：计算
        
        paymentService.pay(order, finalAmount);    // 单一职责：支付（内部通过策略实现OCP）
        repository.save(order, finalAmount);       // 单一职责：持久化
        
        notification.notify(order, finalAmount);   // 单一职责：通知
    }
}

// 具体的支付服务实现，遵循OCP，可以动态增加PaymentMethod
public class PaymentServiceImpl implements PaymentService {
    private final Map<String, PaymentMethod> methodMap;
    
    public PaymentServiceImpl(Map<String, PaymentMethod> methodMap) {
        this.methodMap = methodMap;
    }
    
    @Override
    public void pay(Order order, double amount) {
        String method = order.getPaymentMethod(); // 如 "CreditCard"
        PaymentMethod paymentMethod = methodMap.get(method);
        if (paymentMethod == null) throw new UnsupportedOperationException(...);
        paymentMethod.pay(order.getPaymentDetails(), amount);
    }
}
// 当要增加新的支付方式时，只需新建一个实现PaymentMethod的类，并在配置中注册，无需修改现有代码（OCP）

// 各种实现类通过依赖注入容器组装
```

**重构后的代码如何满足 SOLID：**

- **SRP**：每个类只有一个职责，`OrderService` 只负责流程编排，不关心具体细节。
- **OCP**：通过接口和策略模式，新增支付方式、新的通知渠道等，都不需要修改 `OrderService` 的代码，只需要增加新的实现类。
- **LSP**：所有接口的实现类都可以安全地替换相应的接口，因为接口定义了明确的契约。
- **ISP**：接口被拆得非常小，例如 `Logger` 和 `EmailNotifier` 分离，客户端只依赖他们需要的。
- **DIP**：`OrderService` 依赖的是抽象的 `OrderValidator`、`PriceCalculator` 等接口，而不是具体的类，依赖关系倒置过来，由外部注入具体实现。
